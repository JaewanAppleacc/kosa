# 5. 구조 결정

## 5-1. 점수를 더하지 않고 순위를 합친다 (RRF)

BM25 점수와 코사인 유사도는 스케일이 다르다. 정규화해서 더하면 한쪽 분포가 바뀔 때 가중치가
조용히 틀어진다. 순위 기반 융합은 그 문제가 없고, 상수 하나(k=60)만 남는다.

## 5-2. `find_comparable()`은 항상 한 그룹만 반환한다

Protocol의 반환 타입은 평평한 `list`인데 docstring은 "여러 그룹 반환"과 "그룹 섞지 않음"을
동시에 요구한다. 둘 다 만족할 수 없다.

**섞지 않는 쪽**을 지켰다. 섞인 목록은 화면에서 정상적인 순위처럼 보이지만 근거가 없고,
사용자가 이상함을 알아챌 방법이 없다. 반면 한 그룹만 반환하면 "다른 그룹도 있다"는 사실은
`available_groups()` / `find_comparable_groups()`로 확인할 수 있다. 되돌릴 수 있는 쪽을 골랐다.

내보내기 직전에 `assert_single_group()`을 한 번 더 부른다. 조용히 걸러내지 않고 예외를 던지는
이유는, 이 조건이 깨진 결과는 화면에 나가면 안 되기 때문이다. 조용히 걸러내면 사용자는 일부만
보이는 목록을 전체로 오해한다.

## 5-3. MCP Tool이 `empty`와 `source_missing`을 나눈다

"그런 학과는 없다"와 "아직 모아 놓은 자료가 없다"는 다른 말이다. 둘 다 빈 리스트로 돌려주면
상위 계층이 "자료가 없다"를 "존재하지 않는다"로 바꿔 말하게 된다. 입결 Tool은 학과 자체가
수집 대상에 없으면 `source_missing`, 조건에 맞는 행만 없으면 `empty`를 돌려준다.

## 5-4. `.xls`는 빈 결과가 아니라 명시적 오류

표준 라이브러리로 읽을 수 없다. 조용히 빈 결과를 주면 "개설과목이 없는 학교"로 오해된다.
`ParseError`에 "xlsx로 다시 저장해 달라"는 조치까지 적어 돌려준다.

## 5-5. 외부 라이브러리 없이 표준 라이브러리로 구현

`requirements-lock.txt`에 langchain·pgvector·pypdf가 없고 의존성 추가는 A 결정이다. 셋 다
**인터페이스는 그대로 두고 내부만 교체 가능한 형태**로 짰다 — `chunk.split_text()`,
`VectorIndex.upsert/search`, PDF 추출기. 지금 못 쓴다고 구조를 다르게 짜면 나중에 다시 짜야 한다.

## 5-6. 저장소를 JSONL로 두고 Repository 뒤에 감췄다

DB 도입은 A의 인프라 결정이고 대학알리미 Key도 아직 없다. Protocol만 만족하면 A의 LangGraph
코드는 저장소가 무엇인지 몰라도 된다. JSONL은 diff가 읽히고 리뷰에서 데이터 변경을 눈으로
확인할 수 있다는 이점도 있다.

## 5-7. 빌드 스크립트가 원본이고 산출 JSON은 파생물이다

사람이 손대는 건 `data/raw/`와 각 빌드 스크립트 상단 표뿐이다. `data/master/`,
`data/drafts/`, `data/eval_fixtures/`는 `career_build_all.py`가 다시 만든다.

산출물을 직접 고칠 수 있게 두면 "어느 게 최신인지"를 알 수 없게 된다. 파생물로 못 박으면
재생성이 항상 정답이 된다.

## 5-8. Persona 기대값을 코드로 만들지 않고 손으로 적었다

`career_build_persona_fixtures.py`의 숫자는 답변 시퀀스를 보고 사람이 센 값이다. Evidence
Engine을 불러 계산한 값을 적으면 "코드와 손계산이 일치하는지" 확인하는 의미가 사라진다.
스크립트는 손으로 적은 값을 엔진 결과와 대조해 어긋나면 **파일을 쓰지 않고 멈춘다.**

Persona 4종은 재현하는 상태가 겹치지 않게 설계했다.

| Persona | 노린 상태 |
|---|---|
| 표현·창작 중심 | STRONG · MODERATE · INSUFFICIENT 두 사유 |
| 관계·조정 중심 | STRONG 하나 + 나머지 전부 INSUFFICIENT |
| 실행 중심 | **LIMITED** — 같은 Context·같은 Frame에서만 반복된 근거 |
| 관심 분산형 | STRONG 없음 — "추가 탐색 필요" 화면 조건 |

Fixture는 Persona·기대값·Blueprint를 한 파일에 담아 자기완결적이다. A의 Harness가 다른 모듈을
import하지 않고 파일 하나만 읽으면 된다.

## 5-9. 재생성이 몇 번을 돌려도 같은 파일을 만든다

Manifest의 `fetched_at`/`indexed_at`에 실행 시각을 넣으면 재생성할 때마다 파일이 바뀌어
git diff가 매번 지저분해지고, 정작 **무엇이 달라졌는지**가 안 보인다. 이 파이프라인은
네트워크를 치지 않고 저장된 원문을 읽으므로 실행 시각에 의미도 없다. 그래서 코퍼스
스냅숏 시각(`CORPUS_SNAPSHOT_AT`)으로 고정했다. 실제 수집기가 붙으면 그때는 진짜 수집
시각을 넣어야 한다.

같은 이유로 합성값을 만들 때 파이썬 내장 `hash()`를 쓰지 않는다 — 문자열 해시가 실행마다
달라져 재생성 결과가 매번 바뀐다. `hashlib`로 고정한다.

## 5-10. 스크립트 출력 인코딩을 각자 고정한다

산출물·로그가 전부 한국어이고 대시(—)를 쓴다. Windows 기본 콘솔은 cp949라, 이대로 두면
스크립트가 계산을 다 끝내 놓고 **마지막 print에서** `UnicodeEncodeError`로 죽는다. 결과
파일은 이미 UTF-8로 잘 쓰인 뒤라 원인을 찾기도 어렵다. `scripts/career_console.py`의
`use_utf8_stdout()`을 각 스크립트 시작점에서 부른다.
