# 8. 실무 검토 질문 — 무엇을 증명했고, 무엇은 아직 못 말하는가

이 문서는 발표에서 구현 기능을 다시 나열하기 위한 문서가 아니다. 평가자가 묻는 핵심은
`왜 그렇게 만들었나` 다음의 **`그래서 목적을 달성했다는 것을 어떻게 아나`**다. 아래는 그
질문에 C가 자기 책임 범위 안에서 답할 수 있는 선과, 넘으면 안 되는 선을 함께 적은 것이다.

## 먼저 책임 경계를 고정한다

| 질문 | C가 답하는 범위 | C가 대신 답하지 않는 범위 |
|---|---|---|
| 멀티턴이 실제로 심층화되는가 | 다음 단계가 사용할 근거 데이터의 출처·상태·누락을 구분한다 | 질문 순서, 다음 Trait 선택, 종료 조건의 타당성은 A의 대화·평가 로직 |
| LLM이 충분하다고 보고 멈춰도 되는가 | C 데이터는 LLM의 `충분하다`는 문장을 승인 근거로 사용하지 않는다 | 세션 종료 판단의 전문가 타당도·조기 종료율은 A가 별도 평가해야 한다 |
| 추천 성능이 몇 퍼센트인가 | 데이터 보존율·분류/검토 수·검색 평가처럼 측정한 값만 말한다 | 학생에게 맞는 진로를 맞혔다는 추천 정확도는 현재 측정하지 않았다 |
| 호텔경영 같은 소수 관심도 되는가 | 관광학을 독립 전공군으로 분리했고 전국 학과 후보를 보존했다 | 그 학생에게 관광학을 잘 추천하는지는 Trait→전공 평가가 필요하다 |

**중요한 구분:** 테스트 1,029개 통과, 전국 학과 정규화 24,422건, 생성 결과의 byte 결정론성은
구현 안정성과 데이터 처리 정책을 증명한다. 이것을 **학생 이해 정확도나 추천 적중률**로 바꿔
말하면 안 된다.

## 8-1. “전국 데이터가 많으면 추천도 잘하나요?”

**실제 의문.** 데이터가 2만 건이 넘는다는 사실은 규모일 뿐이다. 학생에게 맞는 학과를 찾는
성능과 무슨 관계가 있는가.

**C가 증명한 것.** 2025 대학알리미 원본에서 4~7년제 학사과정 24,422건을 같은 공식 코드
기준으로 정규화했고, 현재 상태 후보 10,063건과 추천 후보 10,057건을 구분했다. 폐지·야간·
계약과정은 삭제하지 않고 상태와 제외 사유를 남겼다. 따라서 추천 상위 계층은 적어도
`존재하지 않는 학과`, `폐지 이력`, `추천 범위 밖 과정`을 같은 후보로 취급하지 않는다.

**아직 증명하지 않은 것.** 이 데이터가 많아서 개인화 추천이 더 정확해졌다는 인과관계는
측정하지 않았다. 필요한 후속 평가는 `전국 데이터 적용 전/후 후보 누락률`, `정답 후보 포함률`,
`전문가가 적절하다고 본 학과의 Top-k 포함률` 비교다.

## 8-2. “분류가 잘됐다는 것을 어떻게 아나요?”

**실제 의문.** 공식 소계열을 썼다고 해서 학생이 이해할 수 있는 전공군으로 올바르게 묶였다고
볼 수 있는가.

**C가 증명한 것.** 공식 대·중·소계열을 우선하고 이름 유사도로 강제 확정하지 않는다. 하나의
소계열이 여러 전공군에 배정된 충돌은 0건이고, 추천 후보 중 중복 `department_id`도 0건이다.
컴퓨터교육과는 교육학군, 전기정보공학부는 전기·전자군으로 가는 반례를 고정했다. 계약학과
6건도 일반과정과 같은 이름이라는 이유로 합치지 않았다.

**사람이 남아 있는 이유.** 추천 후보 중 분류 REVIEW 1,936건과 N.C.E 1,901건은 자동 승인하지
않았다. 검수 패킷의 `auto_approved_rows=0`, `reviewer_1_status=TBD`,
`resolution_status=PENDING`은 성능 부족을 숨긴 것이 아니라 **현재 자동화가 책임질 수 있는
경계**를 파일로 표시한 것이다.

**아직 증명하지 않은 것.** 42개 전공군 경계에 대한 전문가 일치율은 측정하지 않았다. 다음
평가는 2인 독립 라벨링 후 `일치율`, `불일치가 집중되는 경계`, `검수 후 후보 누락률`을 봐야
한다. 자동 후보 비율만 높이는 것은 품질 지표가 아니다.

## 8-3. “호텔경영처럼 덜 흔한 학생도 되나요?”

**실제 의문.** 준비한 대표 Persona와 전공에 잘 맞는 학생만 성공하는 것은 아닌가.

**C가 답할 수 있는 것.** 전국 분포를 보고 `무역·유통·관광`을 그대로 두지 않고 무역·유통과
관광을 분리했다. 두 집단이 427건 대 417건으로 거의 반반이고 진로가 물류·상사와 호텔·여행으로
갈리기 때문이다. 따라서 호텔경영 계열이 큰 범주의 소수 부속으로 사라지지 않고 관광학 후보군에
남는 **데이터 측 커버리지**는 확보했다.

**C가 답할 수 없는 것.** 질문이 호텔경영 관심을 충분히 포착하는지, 세션이 그 학생에게 관광학을
상위에 제시하는지는 멀티턴 질문·Evidence·Trait→전공 매칭의 결합 성능이다. 현재 C의 Persona
fixture와 42개 전국 전공군만으로 이를 검증했다고 말할 수 없다.

**필요한 블라인드 평가.** 개발에 쓰지 않은 소수 Persona를 별도로 만든다. 최소한 관광·호텔,
농업, 해양, 국방, 특수교육, 종교, 예체능-공학 혼합 관심을 포함하고 다음을 측정한다.

1. 관련 전공이 후보군에 한 번이라도 포함되는가
2. 근거가 없을 때 억지로 가까운 대중 전공에 붙이지 않는가
3. 평가자가 예상한 후보가 없을 때 어느 단계에서 누락됐는가
4. 다수 전공과 소수 전공 사이의 후보 포함률 차이가 얼마나 되는가

## 8-4. “검색 결과가 있으면 근거가 있다는 뜻인가요?”

**실제 의문.** 벡터 검색은 어떤 질문에도 가장 가까운 문서를 돌려준다. 관련 없어도 그럴듯한
근거가 붙지 않는가.

**C가 증명한 것.** 근거 있는 질의 4건과 근거 없는 질의 2건을 분리해 바닥선 0.3을 정했고,
`empty`와 `source_missing`을 구분한다. 공식 문서가 없는 샘플은 `sample://`로 표시해 공식
근거처럼 보이지 않게 했다. 장학금·기숙사처럼 코퍼스에 없는 질문에는 가장 덜 틀린 문서를
억지로 반환하지 않는 검사가 있다.

**아직 증명하지 않은 것.** 현재 문서 6건과 소수 질의는 파이프라인 검증 규모다. 전국 학과에
대한 검색 정확도를 뜻하지 않는다. 공식 대학 문서를 확충한 뒤 학과별 필수 항목 충족률과
라벨 질의 기반 `Recall@k`, `근거 없음 정답률`, 출처 정확도를 다시 측정해야 한다.

## 8-5. “임계값 0.82와 0.3은 실제 서비스에서도 안전한가요?”

**실제 의문.** 작은 fixture에서 맞춘 숫자가 새로운 학교 문서와 과목명에도 유지되는가.

**C가 증명한 것.** 0.82는 현재 Alias의 참 10건과 거짓 9건 사이, 0.3은 현재 근거 질의 4건과
비근거 질의 2건 사이에서 정했다. 감으로 정한 상수가 아니며 스크립트로 재측정된다.

**아직 증명하지 않은 것.** 표본 밖 일반화 성능은 모른다. 그래서 새 Alias·새 코퍼스·형태소
분석기 도입을 재검토 트리거로 둔다. 실서비스에서는 새 데이터가 들어올 때마다 정밀도·재현율을
다시 측정해야 하며, 현재 값을 영구 상수로 설명하면 안 된다.

## 8-6. “실제 서비스에서 가장 먼저 드러날 허점은 무엇인가요?”

| 허점 | 현재 방어 | 남은 개선 |
|---|---|---|
| 공식 학과 홈페이지가 없음 | `department_url=null`, 대학알리미 루트 링크를 학과 링크처럼 쓰지 않음 | 검증된 학과 URL 수집·갱신 책임자 필요 |
| 입결 출처가 검증되지 않음 | 점수를 `null`, 합성값은 placeholder로 격리 | 공식 출처 확정 후 연도·전형·지표별 검증 |
| 융합·N.C.E 학과가 많음 | REVIEW/N.C.E Queue로 분리, 자동 승인 0 | 2인 검수와 공식 교육과정 근거 확충 |
| 2024 파일과 2025 API의 표기 차이 | `NEW/MISSING`을 신설·폐지로 단정하지 않음 | 같은 출처의 2025/2026 비교 |
| JSONL·메모리 검색의 확장 한계 | Repository/Index 인터페이스로 격리 | 사용자·Chunk 증가 시 DB/pgvector 전환 |
| 데이터 갱신 후 과거 결과 재현 | 조사연도·source record·Manifest·Hash 기록 | 운영 버전별 snapshot과 migration 정책 |

## 8-7. C가 혼자 개선할 수 있는 범위

아래는 다른 작업자의 코드·계약·판단을 바꾸지 않고 C 소유 데이터·생성기·평가 fixture·문서
안에서 진행할 수 있다. **이 절은 완료 보고가 아니라 다음 작업의 범위와 완료 조건**이다.

### 8-7-1. “정확도” 대신 C가 실제로 측정할 지표를 고정한다

**왜 필요한가.** 자동 후보 비율이나 테스트 개수만 말하면 추천 성능으로 오해된다.

**C 단독 작업.** 데이터 파이프라인 보고서에 다음 지표를 분리한다.

- 원본 보존율과 정규화 포함·제외 수
- 추천 후보 중 중복 ID 수
- 공식 분류 충돌 수
- REVIEW/N.C.E/범위 제외 수와 사유별 분포
- 검수 패킷의 자동 승인 수
- 동일 입력 재생성 Hash 일치 여부
- RAG 근거 질의 적중과 `근거 없음` 정답을 별도 집계

**완료 조건.** 보고서의 어떤 비율도 `학생 추천 정확도`라고 부르지 않고, 분모·입력 버전·측정
대상을 함께 기록한다.

### 8-7-2. 실패 사례 목록을 정상 산출물로 만든다

**왜 필요한가.** 평균 수치만 있으면 어느 경계에서 틀리는지 알 수 없다.

**C 단독 작업.** 이미 있는 Queue를 다음 실패 유형으로 다시 집계하고 대표 사례를 남긴다.

- 공식 분류 N.C.E
- 융합·디자인·미디어 경계
- 일반과정/계약학과 관계
- 같은 이름이지만 공식 소계열이 다른 학과
- 같은 학과인데 연도별 원본 ID가 바뀐 사례
- RAG 근거 없음·잘못된 학과 문서 혼입 후보
- 과목 Alias 오탐·미탐 후보

대표 사례에는 입력 필드, 현재 판정, 자동 처리하지 않은 이유, 다시 볼 조건을 기록한다. 실패를
없애 보이게 하지 않고 **어디서 사람 판단이 필요한지 재현하는 자료**로 쓴다.

### 8-7-3. REVIEW/N.C.E Queue의 검수 우선순위를 제안한다

**왜 필요한가.** 3,837건을 순서 없이 전달하면 검수 체계가 있어도 실제로 처리하기 어렵다.

**C 단독 작업.** 승인을 대신하지 않고 다음 근거로 우선순위만 계산한 draft를 만든다.

1. 현재 상태 `EXISTING/NEW`인가
2. 추천 후보로 노출될 수 있는가
3. 같은 공식 분류·같은 검토 사유가 반복되는가
4. 공식 중계열·교육과정처럼 추가 판단 근거가 이미 있는가
5. 한 번의 경계 결정이 여러 행에 영향을 주는가

**안전선.** 우선순위는 승인 확률이나 전공 적합도 점수가 아니다. Queue 순서만 바꾸며
`TBD/PENDING`과 `auto_approved_rows=0`을 유지한다.

### 8-7-4. Alias 자동 매핑도 오류 가능 대상으로 감사한다

**왜 필요한가.** LLM을 쓰지 않는다고 자동 매핑이 자동으로 옳아지는 것은 아니다. 사람이 만든
Alias가 틀리면 같은 오류가 결정론적으로 반복된다.

**C 단독 작업.** Master를 바로 바꾸지 않고 별도 감사 결과를 만든다.

- 한 Alias가 여러 canonical 전공에 걸리는지
- 너무 짧은 키가 우연히 다른 학과에 걸리는지
- 동일 학과명이 서로 다른 공식 소계열에 존재하는지
- Alias 자동 매핑과 공식 대·중·소계열이 충돌하는지
- 새 Alias 추가 전후 자동 매핑·REVIEW 변화량

**완료 조건.** 충돌 행은 자동 매핑률을 유지하기 위해 숨기지 않고 review draft로 보낸다. Master
승격은 A 판단이므로 C가 수행하지 않는다.

### 8-7-5. RAG 평가 fixture를 파이프라인 확인용과 성능평가용으로 구분한다

**왜 필요한가.** 문서 6건·질의 6건으로 전국 검색 성능을 주장할 수 없다.

**C 단독 작업.** C가 확인 가능한 공식·비공식 출처를 구분한 상태에서 평가 세트를 확장한다.

- 학과 소개·교육과정·졸업요건·고교 연계·통계별 정답 문서
- 반드시 검색 결과가 없어야 하는 질의
- 이름이 비슷한 다른 대학·다른 학과 문서를 고르면 실패하는 질의
- 정답 문서와 정답 구간을 함께 기록
- `Recall@3/5`, 근거 없음 정답률, 잘못된 출처 반환률을 분리

공식 문서를 확보하지 못한 학과는 합성 문서로 채우지 않고 `source_missing`으로 남긴다.

### 8-7-6. 소수 전공의 “데이터 커버리지”만 별도로 감사한다

**왜 필요한가.** 관광학 데이터가 있다는 것과 호텔경영 관심 학생에게 잘 추천된다는 것을
섞지 않기 위해서다.

**C 단독 작업.** 질문·종료·Trait 매칭을 실행하지 않고 전국 분류 결과에서 다음만 확인한다.

- 관광·호텔, 농업, 해양, 국방, 특수교육, 종교 등 전공군별 현재 상태 학과 수
- 공식 소계열이 전공군 후보로 연결되는지
- N.C.E 또는 REVIEW에 몰려 후보가 사라지는 분야가 있는지
- 수도권·지역, 대학별 분포가 특정 집단에 과도하게 치우치는지

결과 명칭은 `minor-field data coverage`로 고정한다. `minor-persona recommendation
performance`라고 부르지 않는다.

### 8-7-7. 최신 결정과 시행착오 기록을 분리한다

**왜 필요한가.** §7은 실패와 수정 과정이 시간순으로 쌓여 있어 최종 상태를 찾기 어렵다.

**C 단독 작업.** 과거 기록은 삭제하지 않고 README에 다음 세 상태를 붙인다.

- `CURRENT` — 현재 코드와 데이터에 적용되는 결정
- `RESOLVED` — 당시 문제였지만 후속 작업으로 해결됨
- `HISTORICAL` — 실패 원인과 재발 방지를 위해 보존한 기록

최종 발표는 `CURRENT`만 먼저 보고, 질문이 나오면 `RESOLVED/HISTORICAL`로 내려가게 한다.

## 8-8. 협력이 필요해 이번에 건드리지 않는 범위

아래 항목은 중요하지만 C가 혼자 바꾸면 책임 경계·API 계약·화면 의미가 달라진다. 이번 개선에서
코드나 데이터를 수정하지 않고, 필요한 질문과 산출물만 남긴다.

| 항목 | 협력이 필요한 이유 | 협의할 질문·필요 산출물 |
|---|---|---|
| 멀티턴 종료 타당도 | 질문 선택·Evidence·Stop/Continue는 A 소유 | 종료 사유별 로그, 전문가 종료 동의율, 조기 종료·과잉 질문률 |
| LLM 질문 품질 | Prompt·Quality Gate·Backup 질문은 A 소유 | 고정 질문 대비 블라인드 평가, 중복률, 이전 답변 반영률, 유도 질문률 |
| LLM 설명문의 근거 충실도 | Profile·추천 설명 생성은 A 소유 | 허용 Evidence 목록과 생성 문장의 자동 대조, 근거 외 주장률 |
| Trait→전공 추천 성능 | C의 전공 데이터와 A의 매칭 엔진을 함께 평가해야 함 | 블라인드 Persona Recall@3/5, 부적절 후보 노출률, 소수 Persona 격차 |
| 학생 대상 사용성·효과 | 실제 학생·교사 모집과 평가 동의가 필요 | 질문 이해도, 완료율, 진로 명확성 전후 변화, 추천 납득도 |
| 불확실성 화면 표시 | 문구·UI는 B 소유이고 API 상태와 함께 정해야 함 | 충분 종료/최대 질문/근거 부족을 구분한 화면 계약 |
| Master·공개 API 승격 | A 소유 정본과 B 계약에 영향을 줌 | 검수 완료 조건, migration, Mock/OpenAPI 동시 갱신 승인 |
| DB·pgvector 도입 | 의존성·배포·비용은 팀 인프라 결정 | 사용자·Chunk 규모 기준, 운영비, migration·rollback 계획 |

**이번에 하지 않는 것:** A/B 파일 수정, 종료 규칙 변경, Prompt 변경, 공개 Schema 추가,
Master 승격, 프론트 문구 변경, DB 의존성 추가, 실제 사용자 실험. 필요하다는 이유만으로 C가
선행 구현하지 않는다.

## 8-9. 발표에서 답변하는 순서

실무 질문에는 기능 설명부터 하지 않고 다음 순서로 답한다.

1. **측정 대상부터 한정한다.** “추천 정확도가 아니라 C 데이터 파이프라인의 정확성과 안전성을
   검증했습니다.”
2. **실측값을 말한다.** 예: 24,422건 정규화, 추천 후보 10,057건, 중복 ID 0건,
   REVIEW/N.C.E 3,837건, 자동 승인 0건.
3. **실패를 막는 장치를 말한다.** 근거 부족 보류, `source_missing` 구분, 계약과정 제외,
   원본·Lineage 보존.
4. **못 증명한 것을 분리한다.** 멀티턴 종료 타당도와 학생 추천 적중률은 이 수치로 증명되지
   않는다.
5. **다음 평가 설계를 제시한다.** 전문가 2인 라벨, 블라인드 소수 Persona, Top-k 포함률,
   검색 Recall@k, 근거 없음 정답률.

짧게 답하면 다음과 같다.

> C는 “학생을 완벽히 파악했다”를 증명한 것이 아니라, 추천에 들어가는 데이터가 어디서 왔고
> 왜 포함·제외됐는지 재현 가능하게 만들고, 근거가 부족한 3,837건을 자동 확정하지 않는
> 안전성을 검증했습니다. 호텔경영처럼 덜 흔한 분야가 데이터에서 사라지지 않도록 관광학을
> 독립 분리했지만, 그 학생에게 실제로 잘 추천되는지는 블라인드 Persona와 전문가 평가로
> 추가 검증해야 합니다.
